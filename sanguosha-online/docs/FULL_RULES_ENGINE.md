# 完整规则引擎实施基线

本文约束从原 Java 项目迁移全部 66 名武将时的公共实现方式。目标不是把技能条件继续堆入 `game.ts`，而是让所有会暂停的规则都能序列化、恢复、重放校验，并始终由服务端权威裁决。

## 1. 完整范围

- 武将：标准 25、SP 袁术 1、风/火/林/山各 8、神将 8，共 66 名。
- 卡牌：原默认牌堆全部实体牌、牌面行为、装备持续效果及武将对卡牌的改写。
- 技能类型：普通可选技、锁定技、主公技、限定技、觉醒技、觉醒后技能和源码特殊技。
- 流程：准备、判定、摸牌、出牌、弃牌、结束阶段；跳阶段、替代阶段、翻面、额外回合及回合后清理。
- 特殊机制：改判、拼点、额外牌堆、标记、伤害防止/转移、秘密查看、动态技能、距离和目标修正。

## 2. 不可破坏的状态不变量

1. 每张实体牌任意时刻恰好位于一个区域；虚拟牌必须保存全部实体来源。
2. 客户端只提交意图，不能提交伤害、摸牌结果、判定结果或合法性结论。
3. 任一 Prompt 前后的状态都可 JSON 序列化，并在恢复后只执行一次后续效果。
4. 所有随机行为只消耗 `session.rng`，快照恢复后结果可复现。
5. 非查看者不能从公开视图、Prompt、日志或候选数量推导暗牌内容。
6. 旧快照必须显式迁移；不允许依赖 TypeScript 默认值掩盖非法中间状态。

## 3. 可序列化结算核心

### 3.1 事件

统一事件至少覆盖：

- `phase_start` / `phase_end`
- `card_use_declared` / `targets_confirmed` / `card_committed` / `card_finished`
- `card_responded`
- `cards_moving` / `cards_moved`
- `judgment_started` / `judgment_replacing` / `judgment_finished`
- `damage_started` / `damage_changing` / `damage_dealt` / `damage_received`
- `hp_lost` / `recovered` / `dying_started` / `death`
- `pindian_started` / `pindian_revealed` / `pindian_finished`
- `turn_started` / `turn_finished`

每个事件必须有单调递增的 `eventId`、来源、目标、原因和对应实体牌 ID。事件本身只描述事实，不能持有函数或闭包。

### 3.2 触发队列

事件派发后生成稳定排序的 `SkillTriggerRef[]`：

1. 当前回合角色；
2. 按存活座次顺序；
3. 同一角色按武将技能注册顺序；
4. 同一技能内部按目标顺序。

每个引用包含稳定 `triggerId`、`eventId`、拥有者、技能、目标索引和是否强制。锁定技自动执行；可选技生成 Prompt。已消费的引用不得重新生成。

### 3.3 Continuation 与结算栈

任何可能暂停的步骤都保存数据化 continuation，而不是回调：

- `card_use`
- `phase_cursor`
- `judgment`
- `damage`
- `dying`
- `pindian`
- `card_move`
- `extra_turn`

结算栈顶可以生成 Prompt；Prompt 解决后继续同一 frame。嵌套事件压入新 frame，完成后回到父 frame。服务端必须校验 `promptId` 与 frame/event ID，拒绝重复或过期 action。

## 4. 原子牌移动

所有牌区变化统一为 `CardMoveIntent`：

- 实体牌 ID 列表及虚拟牌子牌列表；
- 来源玩家/区域与目标玩家/区域；
- 正面、背面或仅指定玩家可见；
- 原因（使用、打出、弃置、获得、交给、偷取、交换、判定、死亡清理等）；
- 是否属于使用成本或技能成本。

移动流程为 `validate -> cards_moving -> commit -> cards_moved`。枭姬、连营、屯田、固政、行殇等只能监听移动事件，禁止在各卡牌分支重复补触发。

## 5. 用牌意图

`CardUseIntent` 必须保存：

- `useId`、来源、实体成本牌、有效牌种、花色/点数；
- 有序目标、使用方式（使用/打出/重铸）；
- 转化技能与实体来源；
- 当前事件阶段及剩余触发。

流程为：

1. 构造并纯校验意图；
2. 派发 `card_use_declared` 与 `targets_confirmed`；
3. 处理集智、激昂、铁骑、流离等前置技能；
4. 原子提交实体牌到结算区；
5. 进入无懈、响应和效果；
6. 结算结束后恢复实体牌种并移动到最终区域。

延时锦囊、无懈响应和铁索重铸必须按原 Java 时机决定是否产生“使用普通锦囊”事件。

## 6. 判定、伤害与拼点

- 判定牌先进入独立公开判定区，完成鬼才/鬼道等改判队列后才确定结果；天妒、洛神等再决定最终移动。
- 伤害上下文保存来源、目标、牌、属性、原始值、修正值和防止/转移链；每一点伤害触发次数必须与原规则一致。
- 拼点双方先秘密选择，再同时公开；点数修正、胜负和牌移动都在同一可恢复 frame 内完成。

## 7. 阶段、标记与额外回合

回合使用持久化 `PhaseCursor`，区分阶段首次进入和受伤/Prompt 后续接，避免洛神或其他准备技重复发动。标记统一记录所有者、来源技能、可见性和清理时机。额外回合进入显式队列，不能直接递归调用下一回合。

## 8. 私有视图

秘密选牌、观星、遗计、攻心、蛊惑、化身等只向授权玩家投影候选。服务端快照保存真实内容；公共房间广播只包含稳定 token 和公开结果。

## 9. 实施顺序

### 已落地的主公委托与动态技能基线

- 护驾、激将使用统一的可序列化委托状态：请求者、当前提供者、剩余座次、唯一 Prompt ID 与原结算续体均进入权威快照；提供者只能打出自己手中的合法实体牌或拒绝。
- 激将既覆盖主动使用杀，也覆盖决斗、南蛮入侵和借刀杀人等“打出杀”请求；杀的来源、距离、出杀次数、伤害与无双响应数按请求者计算，实体牌只从提供者区域移动一次。
- 伪帝不复制静态技能列表；每次查询都从当前存活主公的有效主公技集合计算，并服从身份、死亡、技能获得、技能失去和技能抑制状态。
- 庸肆的摸牌数按当前存活普通势力数计算；弃牌阶段先精确执行额外弃牌，再重新计算并执行手牌上限弃牌，两个阶段都保存游标，跳过摸牌或弃牌阶段时不误触发。
- 上述状态已接入服务端快照校验、机器人合法推进与桌面 Web 选择界面；规则矩阵中的完成标记仍以第 10 节门槛和自动测试为准。

1. 阶段游标与通用技能选择：洛神、英姿、闭月。
2. 用牌意图与触发队列：集智、激昂、铁骑、流离。
3. 原子移动：连营、枭姬、反馈、奸雄、突袭、行殇、固政。
4. 判定 frame：鬼才、鬼道、天妒、洛神、刚烈、雷击。
5. 伤害 frame：遗计、节命、天香、狂骨、祸首、暴虐等。
6. 秘密选择与拼点：反间、天义、驱虎、制霸、烈刃。
7. 标记、翻面、觉醒和额外回合：林/山/神包。
8. 动态技能与额外牌堆：化身、七星、忍戒/拜印等收尾。

## 10. 单技能完成门槛

一个技能只有同时满足下列证据才可标记完成：

- 元数据、技能类型和显示文本已注册；
- 正常、拒绝、非法、边界及组合规则测试通过；
- Prompt/临时状态可持久化并恢复；
- Web 能完成所有选择且不泄漏暗牌；
- 机器人能合法推进而不死循环；
- 与同事件阶段的其他技能有确定顺序；
- 长局模拟、全工作区检查和生产构建通过。
