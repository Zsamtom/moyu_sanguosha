## 1. 结论与口径

- 原源码共有 **42 个具体 `Card` 子类**。其中 `CardsHeap.add*Cards()` 实际初始化 **41 种、160 张实体牌**；`SanJianLiangRenDao`（三尖两刃刀）有源码，但未加入 `CardsHeap`。这解释了原 `README.md` 所称“41 种手牌”与目录中 42 个具体类的差异。
- 原源码共有 **66 个具体武将类**：标准包 25 名、SP 袁术 1 名，风、火、林、山各 8 名，神将 8 名。原 `PeoplePool.addStandard()` 把火包荀彧误放入默认池并漏掉许褚，详见第 6 节。
- 当前 TS 已建立带 `id`、种类、中文名、类别、花色、点数和伤害属性的实体牌模型，已实现原默认牌堆全部 **41 种、160 张牌**；未擅自加入原 `CardsHeap` 数量为 0 的三尖两刃刀。
- 当前 TS 已实现默认牌堆 41 种牌的牌面原生行为，包括全部 12 种普通锦囊、3 种延时锦囊、11 种入堆武器、4 种防具和 7 匹坐骑；相应结算、拒绝路径和组合规则由 `shared/test` 覆盖。未来武将对卡牌的改写仍按武将技能单独验收。
- 当前默认武将池是 **标准包 25 名 + SP 袁术 1 名**；荀彧只作为火包旧快照兼容元数据保留，不参与默认发将。26 名默认武将均有 ID、包、势力、性别、体力和技能 ID 元数据，并由服务端随机分配。
- 当前已有 **42 个默认池技能行为**接入权威规则：原有 32 个技能，以及奸雄、天妒、遗计、鬼才、反馈、刚烈、突袭、观星、铁骑、流离。标准包 25 名与 SP 袁术共 **26 名默认武将均已整将完成**；风、火、林、山、神共 40 名扩展武将仍为 `metadata_only`。尚未完成：**武将选择、扩展包技能行为和覆盖全部区域/事件的通用技能注册系统**。
- 扩展包的隔离纯规则规划层已完成源码审计和失败封闭测试：风 **83**、火 **82**、林 **153**、山 **180**、神 **193** 个用例，共 **691** 个。该层明确固化同年代规则及 Java 缺陷裁决，但在接入 `GameSession`、持久化、机器人和 Web Prompt 前仍不计为 `live`，不能据此启用扩展武将池。
- `web` 已展示牌面、装备、判定区、横置状态以及已分配武将的名称/势力/性别，并覆盖当前卡牌、装备和已实现技能的成本牌/目标/发动选择；武将目前由服务端随机分配，尚不能选择。

### 2.1 必须先确立的引擎不变量

1. `GameSession` 仍是单房间唯一权威状态；浏览器永远只收到按查看者生成的投影。
2. 所有随机行为必须消耗房间内可序列化 RNG；随机暗牌、武将候选、判定和洗牌不能调用进程全局随机数。
3. 每个 Prompt 必须携带唯一 ID、合法行动者、合法牌/目标/选项和可否取消；服务端按当前结算帧再次校验。
4. 牌移动必须统一经过移动流水线，先校验来源区域，再产生“失去牌/失去装备/获得牌”等事件；否则连营、枭姬、屯田、固政等无法可靠实现。
5. 伤害、失去体力、回复、濒死和死亡必须分开建模。不能继续沿用“体力归零立即死亡”，否则桃、酒、涅槃、不屈、完杀等没有合法插入点。
6. 技能效果不能直接调用 UI 或等待 Socket；规则函数只生成 Prompt/事件并可序列化暂停。
7. 虚拟牌保存实体子牌 ID；结算、弃置、奸雄、巨象、武魂等都以实体牌移动为准。
8. 临时效果必须有明确生命周期（当前阶段、当前回合、下回合开始前或永久），并在回合/阶段边界统一清理。

## 6. 原源码内部不一致：迁移前必须定稿

这些不是 TS 的实现选择，均能在当前文件中直接复核。迁移时应先建立稳定的卡牌/武将 ID，把显示名与行为规范写入测试；不要把明显的 Java 拼写或池配置错误固化为网络协议。

1. **具体卡牌类数量**：目录有 42 个具体类，`CardsHeap` 只初始化 41 个。`SanJianLiangRenDao.java` 存在且 README 列为已完成，但 `CardsHeap.java` 没有导入或添加它；相反，`FangTianHuaJi.java` 会入堆，但 README 的武器表没有列方天画戟。
   - 其 `details()` 还要求发动时弃一张手牌，但 `use()` 实际只选择附近角色并造成伤害，没有执行弃牌；迁移前需决定采用说明规则还是复刻现有行为。
2. **运行入口未启用标准包**：README 说默认配置使用武将标准包，但 `PeoplePool.init()` 和 `GraphicRunner` 都把 `PeoplePool.addStandard()` 注释掉并调用 `addAI()`。66 名武将类存在不等于当前 JAR 默认路径一定能选到；TS 应由明确的数据注册和房间包配置决定候选池。
3. **标准魏将池**：README 与目录把许褚列为标准魏将、荀彧列入火包；但 `PeoplePool.addStandard()` 实际添加荀彧并漏掉许褚。迁移矩阵按 README 与源码目录归包，并把 `PeoplePool` 代码视为待修正缺陷。
4. **紫骍显示名**：`ZiXing.java` 类和 README 对应紫骍，但 `toString()` 返回“赤兔”，会与 `ChiTu` 重名。
5. **神关羽技能名**：说明文本为“武神/武魂”；实际红桃转杀方法注解成 `@ForcesSkill("武魂")`，死亡方法注解成 `@ForcesSkill("梦魇")`。
6. **集智/急智**：黄月英和神司马懿的部分注解使用“急智”，说明文本使用“集智”。应确定唯一技能 ID，显示名可单独配置。
7. **神吕布标记技能名**：技能说明写“狂暴”，方法注解写“暴怒”。
8. **蔡文姬断肠**：`skillsDescription()` 明写 `(half implemented)`；TS 不应以 Java 当前实现作为“完整规则已验证”的依据。
9. **左慈化身粒度**：`skillsDescription()` 写“获得该化身牌的一个技能”，但 `HuaShen.changePerson()` 实际把玩家替换成所选 `Person` 实例，等同于切换整套武将行为。迁移前必须确定技能选择模型。
10. **身份分布不一致**：当前 TS 与 `PeoplePool` 默认表在 3、4、6、9、10 人时不同：

## 7. 推荐迁移顺序与交付门槛

### 阶段 R0：先冻结规范与测试资料

1. 为 42 个卡牌类和 66 名武将建立稳定英文 ID；显示名不参与规则判断。
2. 把 `CardsHeap.java` 的 160 张牌逐张录为数据（牌 ID、类、花色、点数、杀属性），用测试核对每类张数与总数。
3. 对第 6 节每项差异做明确决定；尤其是三尖两刃刀是否入默认牌堆、身份表和主公体力。
4. 建立 Java 行为样例/规则夹具，但对已标注缺陷的源码不得做盲目快照。

### 阶段 R1：通用规则内核（阻塞所有完整卡牌）

按 E01 → E02 → E03/E04 → E06/E07 → E05 → E11 → E18/E19 的顺序完成。验收至少包括：嵌套 Prompt 可序列化后恢复、非法行动者被拒绝、虚拟牌的实体子牌只移动一次、每种伤害都能进入濒死而非直接死亡、临时效果能在正确边界清理。

### 阶段 R2：基本牌闭环

依次迁移完整杀（先普通、再火/雷）、闪、桃的濒死求救、酒。此阶段不能以当前简化杀/闪/桃算完成；须覆盖使用与打出、距离、次数、属性伤害、多人依次求桃和酒的两个使用时机。

### 阶段 R3：锦囊与判定闭环

1. 先做无中生有、过河拆桥、顺手牵羊、决斗等单目标/自目标通用流程。
2. 再做南蛮、万箭、桃园、五谷的全场逐目标结算。
3. 完成无懈可击链后，所有锦囊才可标为完成。
4. 加入判定区、改判、延时锦囊和阶段跳过，再迁移乐不思蜀、兵粮寸断、闪电。
5. 最后用铁索连环、火攻验证属性伤害、横置传导和重铸。

### 阶段 R4：距离与全部装备

先统一实现四个装备槽、替换/失去装备事件及距离算法；再按坐骑 → 武器范围/次数 → 防具 → 杀结算中的复杂武器响应迁移。每件装备必须有装备、替换、临时失效、死亡弃置及与相关技能组合测试。

### 阶段 R5：标准包 26 将（最高业务优先级）

严格按 5.1 的 S1 → S2 → S3 → S4 交付：

1. **S1**：许褚、关羽、张飞、赵云、黄月英、吕蒙、黄盖、甘宁。
2. **S2**：郭嘉、司马懿、夏侯惇、张辽、甄姬、马超、诸葛亮、孙尚香、陆逊、周瑜、吕布、华佗。
3. **S3**：曹操、刘备、孙权、大乔、貂蝉。
4. **S4**：袁术；必须验证伪帝对当前主公技的动态继承，而非复制一份会漂移的技能代码。

标准包完成门槛：26 名都能在房间配置中选择/随机分配；每个技能的可发动与不可发动边界均有规则测试；主公技仅在主公身份有效；断线重连能恢复当前技能 Prompt；任何玩家视图都不会泄漏他人暗牌或秘密选择。

### 阶段 R6：风 → 火 → 林 → 山 → 神

该顺序与原 README 的开发/包顺序一致，也逐步增加机制复杂度。每包必须在启用/禁用配置、武将候选池、规则测试和浏览器文字提示四处同时交付。山包的动态技能/额外回合完成后再做神将；神将最后可复用标记、额外牌堆、觉醒、全局伤害和跨回合效果。
